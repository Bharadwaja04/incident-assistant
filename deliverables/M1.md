## 1. Problem statement and our understanding

People who witness an incident (a water leak, a fire, a fall, a machine failure) have to fill in a long form while they are stressed, in a noisy place, often with gloves on and a phone in one hand. Forms get left half empty, details get lost, and the report is written hours later from memory.

The track asks for an assistant that lets a person simply **say** what happened and turns that into a complete, structured incident report, **running on the device** (Qualcomm Snapdragon 8 Gen 3 HDK, Hexagon NPU), with no cloud dependency.

What we take this to mean: speech is messy ("uh", repeats, self-corrections like "at 6, no sorry, 6:15", background noise); the output is a fixed schema with four mandatory fields (incident type, location, date and time, description) plus optional severity, people, equipment, witnesses, actions and follow-up; the assistant asks briefly for what is missing (at most three questions) and then lets the person finish on screen; the report is a record, so the system must never invent a fact and must show where each value came from; and everything runs locally, with no network and no cloud.

## 2. Target niche and business opportunity

**Niche we are targeting: industrial maintenance and safety personnel in manufacturing facilities.** We chose them because factories face recurring equipment failures and workplace hazards, with consequences ranging from minor disruptions to life-threatening emergencies. Existing research shows these incidents matter both for worker safety and for cost [add 1-2 citations here]. Frontline staff are also the group for whom typing a form is hardest: they are on the shop floor, in noise, often wearing gloves, and they are needed back at the machine.

Our product simplifies frontline reporting through **on-device voice AI**, **structured severity assessment** and **intelligent clarification of missing information**.

**Business opportunity:** sell the solution to manufacturing companies as an enterprise safety-reporting interface, integrated with their existing maintenance and incident-management systems (the structured JSON report is the integration point). On-device operation suits plants with poor connectivity and strict data rules.

## 3. Idea / abstract

A voice-first reporting assistant. The person taps the mic and describes the incident in their own words, pausing as long as they like; the live words appear on screen as they speak. When they tap again, the transcript is shown in an editable box. An AI step cleans the speech, a language model fills the schema, and the assistant asks only for what is still missing. A review screen shows every field with a badge (confirmed, derived, needs checking), highlights the exact words each value came from, and accepts corrections by voice or by hand. On submit, the report is stored locally and the assistant reads a short summary back.

Design principles:

1. **The model proposes, code verifies.** Every value must be supported by the person's words, or it is flagged.
2. **Severity is never asked.** If the person states it, that wins; otherwise it is derived from the incident, with a floor of High for injury, fire, smoke, gas and electric shock. It is shown as a yellow "derived" badge.
3. **Never loop on the user.** After three questions, or when the audio is unusable, the app hands over to the form.
4. **The person stays in control.** Recording stops only on a tap; text and every field are editable.

## 4. High-level approach, pipeline and architecture

```
 mic -> live captions -> Whisper ASR -> AI cleaning layer -> Qwen extraction
                                                                  |
   spoken summary <- submit <- review screen <- checks (code) <- missing-field questions
```

| Stage | What it does | Model / tool |
|---|---|---|
| Capture | Tap to start, tap to stop (no silence cut-off). Live text every ~2 s. | React Native mic (browser on laptop) |
| ASR | Speech to text with word confidences; noise-only audio is filtered | Whisper (base/small on laptop; Large-v3-Turbo or Small, w8a16, on the NPU via the Qualcomm VoiceAI SDK) |
| Cleaning layer | Removes fillers, stutters, repeated words and self-corrections. It may only delete words; a code guard rejects any output that invents words, loses a "not", or drops facts, and falls back to a rule cleaner. | Qwen3-1.7B (small prompt) + guard |
| Understanding | Fills the JSON schema from the cleaned text and the report so far; repairs room names from a list | Qwen3-1.7B Q4_0 (Ollama on laptop; llama.cpp Hexagon backend on the board) |
| Checks | Evidence match, no future times, time parsing, severity floor, confirm low-confidence values once | Plain code, no model |
| Dialogue | Asks the most useful next question (combined "when and where" if both are missing); max 3 | State machine |
| Review, submit, voice out | Badges, highlighted evidence, voice or typed corrections; saves to SQLite + JSON; reads a summary back | App UI; MeloTTS on the board |

**App and hardware plan.** The app is built in **React Native** (Android) for the HDK8650 (Snapdragon 8 Gen 3, Hexagon v75). The UI (record, review, history screens) and the pipeline logic (time parsing, evidence checks, dialogue state machine) are written in TypeScript, so the same code drives the screens. The heavy models are not JavaScript: Whisper (Qualcomm VoiceAI SDK) and Qwen (llama.cpp Hexagon backend, with Phi-3.5-mini via Genie as fallback) run natively on the NPU and are exposed to React Native through a thin native module, or through a local `llama-server` on 127.0.0.1 that the app calls over HTTP. The working prototype runs the same pipeline on a laptop (faster-whisper, Qwen via Ollama) so the logic is built and tested while the board is brought up. The Python reference is checked against exported golden test cases, which the TypeScript port must also pass.

## 5. Planned testing methodology

We test in four phases, each with a pass/fail gate, so we always know whether a change helped.

| Phase | What is measured | Data |
|---|---|---|
| 0. Setup | Pipeline runs end to end, models load, clips and transcripts present | 10 recorded clips with transcripts |
| 1. Extraction | Field-level accuracy against gold answers; hallucination rate (gate: no more than 5% of values unsupported); extraction latency | 25 hard sentences with gold fields |
| 2. Speech | Word error rate of Whisper small vs base on our own voices and venue noise; confidence-based re-ask behaviour | Recorded clips, including noisy-station audio |
| 3. Conversation | Full dialogues: follow-up count (max 3), corrections, confirmations, hand-over to the form, turn latency (p50 under 3 s, p95 under 6 s on laptop) | 6 dialogues, 17 shaky-speech scenarios, 20 disfluency cases, 8 cleaner-guard cases |

Risks we test for: times like "847"; future times; "fire department" mistaken for a fire; Whisper hallucinating on noise; the cleaner dropping a "not"; question loops; long pauses mid-sentence; machine noise.

**Current baseline (rule-based extractor, laptop):** Phases 0 and 3 pass all gates; Phase 1 field accuracy is 0.90 against a 0.85 gate. The same gates are being re-run with Qwen3-1.7B and the AI cleaner on the laptop, then repeated on the board, where we will also measure NPU latency, model size (under 2.8 GB) and peak RAM (under 4 GB). Still to add: more speakers, factory-like noise, and a hidden test set of ~20 cases.
