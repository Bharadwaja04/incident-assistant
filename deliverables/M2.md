## 1. Current approach and changes since M1

The pipeline is unchanged at the top level (tap-to-talk, Whisper, cleaning, Qwen extraction, missing-field questions, review screen, submit, spoken summary). What changed is **who does the understanding**, and the hardware plan.

**Everything that interprets language is now done by Qwen; code only validates.** In M1 a rule-based extractor and keyword rules sat beside the model. We removed them from the app (they remain only as a test baseline). Now:
- **Extraction by tool calling.** Qwen3-1.7B calls `create_incident_report` or `request_missing_info`; the model itself decides which mandatory fields (type, location, time, description) are missing. Extraction only: no generated text, no invented advice or follow-ups.
- **Focused follow-up calls** for a mandatory field the first pass missed: incident type (with a one-line reason), location, time, and severity.
- **Severity is judged, not looked up.** Qwen weighs factors (harm to people, hazard, spread, whether it is ongoing, impact) and the review screen shows its reasons; reasons not supported by the speaker's words are dropped.
- **Time through a function.** Small models cannot do clock arithmetic ("two hours ago" came back as the current time; 10:35 p.m. came back as 20:35). Qwen now calls `resolve_time` with exactly what was said (minutes ago, or hour/minute/am-pm); plain code does the subtraction and the 12-to-24-hour conversion.
- **Vague places are not accepted.** "My room" makes the app ask for a room number, block or floor.
- **Corrections update the fields.** Time and place are re-read from each new utterance, and AI-derived severity and type are re-judged as details are added; fields the user edited by hand stay locked.
- **Checks that remain in code are validation only:** every value must appear in the person's words, no future times, valid formats.

**Speech front end:** 80 Hz high-pass filter and amplitude gate, hallucination filter, a fluency note (long pauses, prolongations) for stuttered speech, live captions, and recording that stops only on a tap.

**Hardware and app plan (updated).** Board: HDK8650, Snapdragon 8 Gen 3. Qualcomm's AI Hub lists ready-made Whisper-Tiny assets for 8 Gen 3; the larger Qwen3-8B is not offered for this chip, so the LLM plan is Qwen3-1.7B (4-bit GGUF) through a llama.cpp/GenieX runtime on the device, with a smaller AI Hub LLM as fallback. The UI is React Native with the logic in TypeScript, using a development build, since Expo Go cannot load native model runtimes; the models sit behind a thin native module.

## 2. Experiments run so far and results

**A. Automated gates (rule-based baseline, laptop; run today).**

| Gate | Result | Target |
|---|---|---|
| Phase 0: test set and contract (25 utterances, 6 dialogues, 10 clips) | Pass | |
| Phase 1: extraction field accuracy | 0.90 | >= 0.85 |
| Phase 1: hallucinated absent fields | 0.00 | <= 0.05 |
| Phase 3: dialogues reaching review / final fields correct | 1.00 / 1.00 | 1.0 / 0.9 |
| Phase 3: shaky-speech scenarios, cleaner guard, disfluency cases | 17/17, 8/8, 20/20 | all |
| Phase 3: turn latency p50 / p95 (text only) | 0.001 s / 0.007 s | <= 3 s / 6 s |

Weakest fields in Phase 1: incident type 0.78 and people involved 0.60.

**B. Live sessions on the laptop** (Whisper small and Qwen3-1.7B through Ollama, about 10 saved reports). Whisper small transcribed well; the model side showed these failures, each of which we fixed:

| Observed failure | Cause | Fix |
|---|---|---|
| Time asked again after "8.35 p.m." | Model answered in a non-ISO format | Lenient reshaping, then the `resolve_time` function |
| "Two hours ago" saved as the current time; 10:35 p.m. saved as 8:35 p.m. | Model arithmetic | Model passes numbers only; code computes |
| Bulldozer collapse typed as "IT outage" | Weak category prompt | Full category definitions |
| Severity reasons mentioned an injury nobody reported | Model invention | Prompt: stated facts only, plus a check that reasons use the speaker's words |
| Location left empty or copied from a prompt example | Example leaked into the answer | Examples removed; vague-place question added |
| Time correction ignored when adding details | Time only read if missing | Re-read time and place on every utterance |

Speech errors seen: "valve" heard as "value", "bulldozer" as "blizzard", "conveyor" as "convoy". These are fixed by the editable transcript; we are testing a vocabulary hint.

**Not yet measured (stated plainly):** the LLM gates (Phase 1 and 3 with real Qwen), word error rate (Phase 2), and everything on the board. The fixes in table B were verified with scripted model replies, not yet re-scored on real Qwen.

## 3. Progress on testing

The four-phase gate harness from M1 is working, and a golden test file (14 groups of input/output cases) is exported so the TypeScript port can be checked against the Python reference. Live testing is by voice on the laptop. Board testing is at the start: the board is connected and the Android SDK/NDK and adb setup is in progress; the microphone and model-loading checks are next.
